# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

GBCformer runs the Game Boy Color in a Llama checkpoint: Meta's Llama layer set. The claim of record is the one model as one uniform GGUF in unpatched llama.cpp b12070 on Metal, built with llama.cpp's own default options; the layer-shaped (trimmed) GGUF with three patches (`tools/stock-llama/layer-shapes.patch`, `stream-slices.patch` and `stored-runs.patch`, applied in that order by `tools/stock-llama/run.sh <dir> <rom> setup`) is a speed-up only ("What runs where", below). It computes the SM83 CPU, memory, PPU, APU and control logic. A compiler writes all of the weights; none are trained. The host shows frames, plays samples, reads the buttons and paces time; the reference devices it also keeps (ordinary Rust) run only in lockstep or when labelled. The design follows NESFormer's idea of compiling a CPU into transformer weights, but shares none of its code or architecture.

- `docs/perf-log.md` is the performance decision trail: the benchmark workload, the gates and every measured change.

## What runs where

Everything here is llama.cpp b12070 (commit `00f113ec`) on an M1 Max, and the model is the current one model, `ff86dde7`, unless a row names another. The unpatched source appears in two builds. What the proof of record covers, and what it does not:

- It starts at the hand-off state the host sets up without a boot ROM (`boot none, warmup 0` in its checkpoints). It does not run the boot ROM from power-on.
- Every pass runs every weight, but a pass attends its stream's scope of the cache's cells, not every cell (`docs/stock-llama.md` §13, "The scopes narrowed"). Each scoped GBC CPU, PPU and length pass was held to the lines that the engine's record says its heads read. No pass was decoded a second time over every cell.
- Yellow lends no lines in 300 frames, and the pixel stepper's stream has no pass, so the proof of record exercises neither. Two separate runs on the same build and file do, each one frame of Zelda DX after frames the reference interpreter ran (`--warmup`). Frame 7 lends lines: all 21,110 passes equal the engine's record, 438 lines lent and put back in 876 write-record decodes, the 424 cells that the harness compares after the put-back all equal to the cells found, and 2,250 write records, those 876 decodes and 160 reader records each decoded both ways with 0 cells and 0 rows that differ. Frame 25 has the stepper: all 14,982 passes equal, 3,392 of them stepper passes that draw one line. Not run in unpatched llama.cpp: a stepper pass in Yellow, Crystal or Mario DX (their first is at frame 1,154, 3,087 and 1,627), a stepper pass on a DMG on `ff86dde7`, a frame with both loans and stepper passes, and more than one frame of either.
- The harness binary had its library search path changed to the run's folder and was signed again ad hoc. The run's `STATUS` file records the sha1 before and after (the run's folder is local and not in this repository; `docs/perf-log.md`, "The proof of record on `ff86dde7`", quotes it).
- The first proof used the BLAS-off build. On Metal the two builds gave the same rates over 3,000 passes (`docs/perf-log.md`, "Round 14").

The Mac CPU rows differ by build options only: no source patch, and no file or weight differs. With BLAS off, the Arm build sums products in 16-bit floats, and a whole-model pass runs every other stream's units at every position, where some of their sums pass 65,504, the largest 16-bit float (1,863 of the model's 76,143 gate rows can: `cargo run --release --example f16foreign`). Metal sums in 32-bit floats, and so does a build without FP16 vector arithmetic (`+nofp16`). That Accelerate is what makes the default build right is inferred from these runs; which multiplies it takes was not traced. Every Mac CPU run here started from a cache that Metal prefilled.

In every row a pass decodes its stream's own group of tokens (`STOCK_GROUP=own`), never the whole sequence, and that is what both proofs ran. Over the whole sequence the other parts' positions carry those parts' modes over this stream's bytes, values no part computes exactly, and on Metal the rows of a GBC CPU pass then differ from its own group's (measured on `ff86dde7` and on `7b064d51`: 148 rows at the first GBC CPU pass; `docs/stock-llama.md` §12a).

## Project rules

- **No Python.** The project and its tooling are Rust, shell and TypeScript (Bun). Python-only references such as Needle and NESFormer may be read but are not run.
- **Keep the model small.** Report size as dense parameters and as nonzeros. The checkpoints use Meta's Llama layer set.
- **The model must really compute everything.** No core, device or host shortcut may silently supply a result. Any frames run on the reference interpreter are labelled, as `--warmup` labels them.
- **The weights compute every effective bank.** The host places a record only by bit concatenation (region, bank, offset) of values the model emitted, and never applies a mapper rule. DMA copies follow the same rule. The machine logs bus addresses, and a memory pass of its own translates each DMA line's source and destination (`DS DD` in, `DP DQ` out, `MemCheckpointCore::dma_line`), so the bus map, VRAM's bank and the RAM mask are the weights'; a fetched byte the host serves comes from the port the model emits for it (`FP`), and a write a second device hears names it in a second port (`WD`) (`docs/host-in-weights.md` §6).
- **No ROM, save or boot ROM is ever committed.** The gates run Pokémon Yellow (`pokemon-yellow.gbc`, sha1 `cc7d0326…`) and the other games named below from files you supply. `.gitignore` excludes `*.gb`, `*.gbc`, `*.sav`, `*_boot.bin` and `vendor/`.

Features: `gbc` (every Game Boy module, and the GBC rules in `memory::layout`) and `frontend` (minifb window, cpal speaker, frame pacing, needs `gbc`) are on by default, and the `gbcformer` binary needs both. Without `gbc` the crate is the inference core: the dense pass, the engine, the cells and the GGUF reader. On Linux the frontend needs `libasound2-dev` and `pkg-config` installed, since cpal builds against ALSA.

`vendor/` (gitignored) holds SingleStepTests/sm83 at `f9c30210`, the blargg `cpu_instrs` and `instr_timing` ROMs (`run <rom> --frames 4000`), blargg `dmg_sound` 01-04 in `vendor/blargg/dmg_sound/` (`run <rom> --frames 2000 --core ref --hardware dmg --dump out.ppm`; they report on screen, not serial), and dmg-acid2 and cgb-acid2 (`tools/acid2.sh`).

## Architecture

**Pipeline.** Circuit IR (`circuit.rs`), then the GBC CPU circuit (`sm83/`, its decode, datapath, alu and fields stages over one `G`), then the Llama checkpoint (`llama.rs`), then the fast engine (`engine/`). The CPU and host meet at the contract in `step.rs`.

- **`step.rs` contract.** Each step is a HALT wake-up, an interrupt dispatch or one instruction.
  - The host passes the three fetched bytes (fetch k at `Cpu::fetch_address`: pc, pc+1, pc+2, or under the HALT bug pc, pc and pc+1, each read at its own M-cycle), plus IE and IF. With memory on the host (`--weights cpu`) the host reads them at those addresses, the HALT bug's fetch rule from the CTL bit the model emitted; with memory in weights the model fetches its own.
  - The core asks for up to two data reads, then returns the next CPU state, up to two writes, the M-cycle count and IF acknowledgements.
  - What else the host must know of the step in hand is one value, `StepFacts` (`Core::facts`): which reads the host serves, whether the core reads the bus and translates its own accesses, and the ports and physical addresses the model emitted for its fetches, reads and writes. A core without memory returns `StepFacts::BUS`; the two memory cores keep theirs current where the request and the outcome settle (`request_facts`, `outcome_facts` in `sm83/abi.rs`), and `Lockstep` and `AnyCore` forward the one reference.
  - Timing is counted per step. While halted with nothing pending, the host advances time without calling the core.
  - `reference.rs` (interpreter), `sm83::CircuitCore` (IR evaluated directly) and `sm83::CheckpointCore` (the model) all implement the same `Core` trait.
- **`circuit.rs`.** Every wire is 0/1 or, in the GBC CPU circuits, a nibble (0..15, `docs/byte-channels.md`), and every node is `Σ coef·[affine form ≥ θ]`, or with `ramp` `Σ coef·max(0, form − θ + 1)`. NOT, constants and sums of mutually exclusive wires are affine and cost nothing. One level is one transformer MLP.
  - Nibbles: `input_nibbles` (two level-0 wires per input byte, which layer 0 gathers as four bits weighted 1, 2, 4, 8), `value_mux` (one ramp per case), `output_nibbles` (a field as two nibbles, routed into routes 0 and 1 and scored by the nibble LM head). The compiler widens hidden when the norm's bound needs it (`llama::norm_squares`).
  - Wires carry their real ranges, since folding can leave a wire in {−1, 0} with +1 carried in its form.
  - `bit_of` builds a one-level staircase, and `sum_bits` builds a one-level adder.
  - `Circuit::schedule` (run at the end of `sm83::build_with`) moves nodes within their slack to narrow the widest level, which sets every layer's MLP width. Depth, heads and steps are unchanged.
  - `Circuit::fit` (run after it, memory circuit only) is a deterministic local search over the same moves. It caps the live wires at `Model::wire_budget` (the channels hidden 1,024 leaves), so `Circuit::channels` can put a wire in a dead wire's channel, then minimises the MLP width with the clearing units, then the changed (wire, reading layer) pairs per pass weighted by `src/sm83/changes-memory.txt`. Re-record that table after a circuit change: `GBCFORMER_UNITS=1 GBCFORMER_WIRE_CHANGES=<file>` on text.sh and overworld.sh with `CORE=model-mem`, averaged. The host's live wires cannot fit hidden 1,024 (256 one-hot token channels), so the host circuit is not fitted.
- **`sm83/`.** Opcode one-hots sit at level 1 (CB one-hots come from op1's nibbles at level 2). Every control signal is a linear sum of one-hots. Each output field is one final mux, with "keep" as the complement case.
  - `sm83::build` and `build_mem` give the nibble circuits (`d4.rs`): the decode, the fetch, the address translations and the memory heads' queries are 0/1 wires; the datapath, the ALU and the byte fields are nibbles, and an add costs only its carries. They are the only GBC CPU: the 0/1 circuits were removed, setting `GBCFORMER_BITS` fails with a message, and the older `GBCFORMER_D4` is ignored (`sm83::refuse_retired_switches`).
  - Memory mode reads bytes by column select (`docs/hardware-shaped.md` §20): one head per (line, lane) a byte can come from, its query `Query::gated` (the line when its word line is 1, VOID's zero line when 0), every column of a byte driving one bus (`Circuit::bus`, `head_onto`); the opcode, OP1, OP2 and read 0 are buses. The engine reads a query bit by its sign over [−1, 2], shares a row's address among its columns, and diffs a bus once.
  - The I/O page and IE translate to `layout::IO` at each register's port code (`layout::io_code`, bits 7..10, the low bits passing), unmapped registers to IO block 0 (0xFF), the unusable area to VOID, VBK and SVBK reads to `layout::TAB` at their bank bits, the MBC3 clock (MAPPER bit 5) to its port and latch; the host dispatches by `layout::port` (`docs/host-in-weights.md` §3 step 2). LDH A,(n) and LD A,(C) read through `RFF`, a gated FF-page translation on the rare heads, so the port table reads a fetched byte only when an instruction addresses the page.
  - Slot ABI: `sm83::Sm83` implements `checkpoint::SlotAbi` with the `slots!` enums `In` (20 bytes, D0/D1 late), `Rq` (7: the two read addresses, `RQ`, and the M-cycle each read (`RC`) and write (`WC`) falls in, slot 0 in bits 0-2 and slot 1 in bits 4-6) and `Out` (22), typed encode/decode and `needs_late`. The memory circuit's inputs add `AS0` and `AS1`, each data access's bus state where the host predicted it differs from the step's start (a nibble per access: VRAM locked, OAM locked, OAM DMA blocking, and bit 3 to replace the step-start state); its `RC` bit 3 says the step reaches VRAM or the FE page by a data access, and its `WC` bit 3 that an operand fetch's line does (each access's lock mask, `transport::Asked::masks`). The host predicts each access's state from the control model's lock spans and its `DY` output (160 − DI', the M-cycles OAM DMA still blocks), asks again under the overrides, runs the devices to each access's M-cycle, and keeps each write record there (`Core::land_write`); `docs/hardware-tests.md` §4.1.
  - `CheckpointCore<M>` is `checkpoint::CheckpointDevice<Sm83, M>`; `sm83::checkpoint()` builds the CPU one. The device decodes in one masked-diffusion pass. A second pass runs only when the model asks for memory reads: about 3% of steps during boot and about 24% in gameplay. Without a GBC CPU or memory lockstep, the memory core leaves out of its passes the result slots that only the audit reads (`MemCheckpointCore::without_audit_slots`).
- **`apu_circuit/`.** The APU in weights, its own checkpoint (`docs/apu-in-weights.md`). One pass is one segment: at most one register write, at most one frame-sequencer step (from the control logic's edge), M-cycles at one speed that finish up to 22 channel ticks, then a sample or a CPU read. The model turns M-cycles into ticks (`EV` bit 3 the speed) and keeps the tick's phase and a waiting step in its state (`half`, `pend`, §14). The timers advance by closed forms over the tick count.
  - Slot ABI: `Apu4` with 55 inputs (50 state bytes packed by `fields::FIELDS`, then `WA WV EV D RA`), no request, no late slots, and 55 results (the next state, the stereo mix `SL0 SL1 SR0 SR1`, the read's byte `RV`). The mix is the chip's digital output (`machine::apu::Mix`, the DACs through NR51 times NR50's volume). The board's high-pass filter after it is presentation, and `Machine::take_samples` applies it (`machine::apu::HighPass`) once, whatever holds the APU slot, as the host maps the PPU's colours to RGB. `RV` is the readback in weights: register masks, NR52's status and wave RAM through channel 3's position, on DMG only in the tick the channel read it (state bit `jr3`; `docs/hardware-tests.md` §3.1).
  - `ApuModel<E: Segments>` cuts the M-cycle stream as `Apu::mcycle` orders its events (the sample clock counts real time per M-cycle) and runs one pass per segment; `ApuLockstep` runs `machine::apu` beside it and compares state, mix (before the filter) and read after every pass. `CircuitSegments` evaluates the circuit directly for tests.
  - The read bridge: every bus read of FF10-FF3F calls `AudioDevice::sync` first, which closes the open segment with that read, so the CPU sees the APU at its M-cycle (Yellow reads 0.2 to 0.6 times per frame).
  - `worker::Worker` (native only) runs the device on its own thread up to about two frames ahead of the CPU and waits for it only at those reads; `GBCFORMER_APU_THREAD=0` keeps it inline. The sample instants are the host's audio clock.
- **`ppu_circuit/`.** The PPU's line renderer in weights, its own checkpoint (`docs/ppu-in-weights.md` §9, §10). One pass per visible line (two on CGB, one per byte of RGB555): inputs `LY WLN FLG`, 58 memory heads reading its own VRAM, OAM and display image (the display registers' constant head, the OAM scan's shared heads, plus positional heads the engine serves per position, which give each pixel its own map, attribute and tile-row line for the background and the window and its palette line, as the fetcher reads them, `docs/hardware-shaped.md` §13), each pixel's final colour at 160 output positions that share the per-pixel weights (each reading its x from the position wires), and the window's counter and arming after the line (`WLN'`, `WAR'`), which the model threads to the next line.
  - The image starts from the machine's at the hand-off and follows the CPU side's write and DMA records to VRAM and OAM (`engine::Memory::video`) and the bus's display byte writes (`layout::PAL`: palette RAM, BGP, OBP0, OBP1, then LCDC, SCY, SCX, WY, WX), applied at each line in the order the CPU's thread kept them, so a line sees exactly the records kept before its mode 3.
  - `PpuModel` draws, maps each colour to the screen's RGB (presentation) and under `--lockstep ppu` holds every line's 160 colours and the window state to `machine::ppu`'s, the first difference stopping the run. `worker::Worker` (native only) runs it on its own thread, handed 8 lines a wake; VBlank only asks for the frame, and the machine's thread waits when the frame is read (`Session::frame`) or at a display byte read (BGP, OBP0, OBP1, BCPD, OCPD, LCDC, SCY, SCX, WY, WX). `GBCFORMER_PPU_THREAD=0` keeps it inline (`Inline`).
  - `machine::ppu::Renderer` is the seam: the PPU keeps the reference's display bytes and window counter and hands each visible line and each display byte written over (`display_write`); a display byte read with a renderer comes from it (`display_read`), held to the reference under lockstep. It keeps no clock: the machine calls `render_line(ly)`, `end_frame()` and `lcd_off()` when the control logic's timing signals them.
  - Writes during mode 3 (`docs/ppu-in-weights.md` §13, §14): the reference draws each line with a pixel FIFO (`machine::fifo`, SameBoy's fetcher). The length checkpoint judges each display write while a line is open (`fifo::judge`), and a line a write can change is drawn by the stepper (`ppu_circuit::stepper`, one pass per FIFO step, its own checkpoint and the one model's sixth stream) in place of the scanline pass. Mode 0 begins at `fifo::mode0`: SCX's fine scroll rounds there, not in the FIFO's dots.
- **`transport.rs`.** The host's side of the streams, in the inference core and shared by the full program and the minimal runner: the countdown that cuts the control stream into passes (`Spans`: horizon, scheduled mode-3 starts, edges, the look-ahead span; `Start::place`), the control stream's passes as the bus drives them (`Passes`: `pass_with`, `pass_alone`, `cut`, `stop`, `advance`, the further blocks of a general-purpose copy, the renderer's flags, STOP's outcome), the bus state an access sees ahead (`bus_state`, `held_lock`), the copies a pass hands over (`Run`, `Copy`), the one order a block's signals apply in (`Signals::apply` through a `Sink`), the block loop with its stop and stall (`advance`, `Blocks`), a step's accesses at their M-cycles (`settle_accesses`, `Timeline`, behind `Accesses`), block copies held to a step's end, the battery tracker and the board filter. `device::{Copy, Signals}` are its types; `ControlModel`, `Machine` and `step::step` run it, and so does `tools/runner`.
- **`checkpoint.rs`.** The generic two-pass protocol: `SlotAbi` names a checkpoint's input, request and result slots and its LATE input range; `CheckpointDevice<A, M>` masks, decodes, fills the late inputs and decodes again, knowing nothing of the GBC CPU.
- **`sequence.rs`.** A device's tokens as a handle. `Sequence::set` is the only write and records the position, so a pass (`Denoiser::fill_seq`) places only the positions that changed and writes back only the positions whose decode ran again (`Sequence::fresh`); the device keeps each slot's last byte. The sequence's stamp names its last pass: an engine or view holding another stamp compares the whole sequence and decodes every position again. Under the step oracle, and in debug builds and the library's unit tests, every pass also compares the whole sequence with the placement and every stored token with the engine's; a plain release run does not. `Positions` is a fixed list with an id. `fill_into` stays for slices (tests, the minimal runner).
- **`device.rs`.** The peripheral contract: `Device::{read, write, advance, horizon}`, with everything another device must see passing through `Signals` (the speed at block start, the frame-sequencer edge at its last M-cycle, the renderer's entry points the PPU's timing calls for, requested memory copies); the M-cycles the GBC CPU stays stopped are the control logic's `Lines::owed`, a total its passes emit. The reference devices are `machine::apu` and `machine::control::Control` (which owns `timer`, `io`, `dma` and `lcd`).
- **`llama.rs`.** The checkpoint and a dense forward pass that follows HF Llama semantics; this pass is the oracle. Exactness holds by construction, in f16 storage as in f32 (`docs/stock-llama.md`; `Tiles::F16` rounds every matmul input, query, key, value and softmax weight to f16, and `Model::check_f16` checks every weight):
  - The residual holds a wire of value v as `v·UNIT` (UNIT = 2^-7) and `rms_norm_eps` = 2^14 dominates the norm, so every norm divides by exactly 2^7, and with the norm weight 2^14 every matmul reads the wire's integer. Two constant channels (1 and 64) carry the biases.
  - Integer weights scaled by powers of two keep every activation an exact integer. Every circuit step must fit an f16 unit pair: coefficients and live side at most 511, bias at most 32,255 (`Circuit::f16_ok`); `node_at` orients and splits wide steps by byte digits, `bit_of` takes wide staircases a byte at a time, and `examples/f16census` lists what still does not fit.
  - Steps are written as `relu(K(s−θ+1)) − relu(K(s−θ))` with K = 128, where SiLU is exactly ReLU. The second unit is dropped when s ≤ θ.
  - Every checkpoint without input one-hots has one key and value head (HF `num_key_value_heads = 1`). Layer 0's gathers share one key, which codes each input group on two low-frequency dims (`gather_code`), and one value, the four lanes. Every memory head shares the address key and the value, the byte's two nibble one-hots. Every token of a group sits at one position (`Model::group_position`), so a gather's four keys are bit-identical and each weighs exactly 1/4. A last routing MLP moves each output position's field into 8 route channels, and the LM head scores those against 256 shared byte tokens.
  - Inputs come before outputs, so a causal mask gives identical results.
  - Position wires (`Circuit::positions`) read an output position's slot identity instead of a wire channel, so units reading them compute a different value at each output position (the PPU's pixels).
  - Channel reuse: when it saves a block of 1,024 channels (the memory checkpoint), wires share channels in turn (`Layout::wire_ch`, `occupants`). One unit per reuse subtracts the dead wire, `−[x ≥ 1]` or `[−x ≥ 1]`, reading only that channel, in the emptiest MLP between its last reader and the next write.
- **`engine/`.** Produces the same tokens as the dense pass, much faster. The template path computes the circuit layers once per pass. A shared dense channel is one virtual channel per occupant (`Segments`): clearing units are recognised as units that read the channel they write, proven exact on a range around 0 (guarded per pass), and dropped; occupants are numbered `hidden + wire`, the creation order, for locality. Integer-exact mode is checked on the weights at build time and on wire values at run time; under it, summation order is free and evaluation is incremental (only changed channels are scattered). Every shortcut has a guard, and a failed guard falls back. The reasons are in `docs/perf-log.md`.
  - Modules: `int` (`Cols`, `IntLayer`, `Segments`, the bounds; `IntLayer::new` is the only constructor and its fields are private, since `Marks::layer` indexes its tables unchecked), `plan` (`Plan { t: Template, mem: Option<MemPlan> }`: `Plan::check` from the weights, `Plan::prune` to one stream's `View`, both ending in `Template::index`, which derives the reader bits, layer-0 rows and wires), `positional` (the per-position stage's build), `layer0` (the q/k/v cache and the attention diff), `view` (`StreamSpec`, `View`), `records` (the memory checkpoint's index, KV cache and oracles), `cells` (per cell what a lookup reads of its K/V rows, and the write-record memo) and `rows` (the rows themselves, written at once or, for the GBC CPU's stream in a session, by a worker thread in record order: inference management, `docs/perf-log.md` "Round 5b"), `stats` (`Stats`, `Refusal`), and `run`, the per-pass path in one module: `Marks`, `State`, `fill_fast`, `advance`, `memory_reads`, `decode`, `Positional::advance`.
  - The positional stage (`Positional`): units that read a position wire, or a wire such a unit writes, leave the template and run per output position after the shared layers, specialised at each: the slot identity folds into the bias, and a unit whose gate cannot reach 1 over its inputs' declared ranges (`Model::wire_ranges`) is left out there. The pass refuses any read wire outside its declared range, which guards that pruning. A checkpoint without position wires has no stage. The positions split into parts of consecutive blocks (`GBCFORMER_POS_PARTS`, default 4) that run side by side, part 0 on the calling thread and the rest on `engine::pool::Pool` helpers (native only).
- **`machine/`.** The host, in DMG or CGB mode (`--hardware dmg|cgb|auto`; auto follows header bit 0x143.7): the reference bus is the range-to-device table `route` (with memory in weights the host instead hands each I/O access to the device `layout::port` decodes from the physical address the model emitted: `Bus::read_port`, `write_port`, and `write_memory` for the shadow copy of a recorded write), and `Machine::advance` is the scheduler: every device advances once per block, blocks never exceed the smallest `horizon` (one M-cycle while OAM DMA copies; never past a visible line's mode-3 start or line 144), and the block's `Signals` are applied after it (the renderer's entry points, IF bits, copies, stall). Devices: `cart` (ROM-only, MBC1, MBC2, MBC3, MBC5; the MBC3 clock is control logic), `ppu` (VRAM, OAM, the display registers and the line renderer: RGB frames, CGB palettes and attributes), `control` (below, with `lcd`, the PPU's timing), `apu` (two squares with sweep, wave, noise, frame sequencer on DIV bit 4 (bit 5 at double speed), 48 kHz stereo mixes, which the machine's `HighPass` filters to samples (presentation); advanced per M-cycle in `Machine::advance`, the one place time moves, with the speed and the control logic's frame-sequencer edges in `Signals`, so halted and HDMA cycles count too; the machine's APU slot holds it or the `AudioDevice` that replaced it at the hand-off, and audio in `play` and `run --wav` comes from whichever holds the slot), `io` (joypad, serial). CGB double speed: STOP with KEY1 armed switches speed (`Control::stop`), and each block's M-cycles map onto 4-dot ticks for the PPU's timing (counted in 2-dot halves in `control`) and the APU (which takes M-cycles and `Signals::double` and keeps its own tick phase: two M-cycles a tick at double speed; DIV, held in the switch's pause, reaches it only as the control logic's edges); the timer, serial and OAM DMA count M-cycles, so they run twice as fast, and an HDMA block stalls 16 M-cycles; frames are emulated time (`Machine::halves`). `save.rs` writes battery saves atomically, natively only. `machine/` must build for `wasm32-unknown-unknown`: no fs, time, threads, minifb or cpal. Sound reaches the speakers only in `play`, through cpal (native only); `run --wav` writes it to a file instead.
- **`machine::control` and `control_circuit/`.** `Control` is the reference control logic: the timer, IF and IE, P1 (buttons as a host input), serial, OAM DMA and HDMA control (which bytes move and when, and the stall; the bus performs the copies), KEY0, KEY1 and the speed switch (STOP, the speed, the pause), SVBK, the palette index registers BCPS and OCPS (`PaletteIndex`: which palette byte a data port reaches, and the mode-3 lock), the PPU's timing (`machine::lcd`: LY, LYC, STAT, the mode, the VBlank and STAT interrupts, and when a line is drawn, the frame shown and the screen blanked; STAT, LY and LYC route to control, and an LCDC write reaches both it and the PPU) and an MBC3 cartridge's real-time clock (`machine::rtc`: its own copies of the RAM enable and select, the latch, halt, the counting with its carries, the 9-bit day counter and its sticky carry, register writes and reads). On a board with a clock the machine routes 0000-1FFF and 4000-7FFF writes, and A000-BFFF accesses while the cartridge's select names a clock register, to the control device (`Cartridge::clock_hears`, `clock_at`); `Machine::set_time` hands it the wall time elapsed as days and the time of day (`ControlDevice::elapse`, a host input), and a save's 48-byte footer comes from whichever device holds the clock (`ControlDevice::clock`). `ControlDevice` is its contract; the machine latches the device's `Lines` (IE, IF, horizon, DMA active, SVBK, the speed, the pause and the wake bit) after every call, so hot reads are field loads. `control_circuit/` compiles the same logic into its own checkpoint (`--weights control`), one pass per span of M-cycles ending in an event or at the model's horizon; events the ticks cannot touch run in place over an empty span. `ControlLockstep` holds it to `Control` after every pass and advance (state, reads, bus requests, lines). Where only the PPU's mode-3 starts can need a pass before line 144, a pass schedules up to eight of them (`control_circuit::Schedule`, whose first start, period, count, each start's line and the position within that line are all model outputs) and the host counts down to the first and then the period from each, calling the renderer with no pass (§19). Each pass also emits the M-cycles to the frame sequencer's next edge, a drop when a DIV reset or switch clears a set bit, and the HALT wake bit (`FE0 FE1`, §22); the host cuts a block at each edge (`Signals::edge`) and skips the GBC CPU's pass while halted and the bit is clear (`Bus::wake`). `H` is M-cycles, which the circuit shifts into halves by its own speed. Every DMA transfer is model output (§21): a pass names each run of OAM DMA bytes within an 8-byte OAM line by its source page, line and a bit per byte (`DM` for the span's earlier M-cycles, landed before a line the pass draws, `DL` for its last; the destination `FE00 | line | j`), ending a run at the line's end, every line start and mode-3 start, every event and every CPU access the transfer blocks (`ControlDevice::cut`), a pass names at most one HDMA block by its source and destination bits 15-4 (the host enumerates the 16 bytes by their low four bits), a general-purpose transfer's blocks after its first are in-place `Event::Block` passes while the state's `GD` bit (HDMA3 bit 7) is set, and each pass emits the stall (`SS0 SS1`: a block's 8 or 16 M-cycles, or the speed switch's pause) the machine runs. `docs/control-in-weights.md`.
- **Hardware rules and the boot ROM.** `--hardware cgb` runs a DMG-only game in compatibility mode (`ppu::Mode::Compat`, the PPU checkpoint's FLG bit 3). `--boot FILE` runs a boot ROM you supply from power-on (`Machine::power_on`; `*_boot.bin` is gitignored and never committed; the memory checkpoint maps it itself: BOOTING, UNMAPPED, COMPAT and KEY0 are its registers, bank 0 while it is mapped is `layout::BOOT`, a 16 KB image of bank 0 with the boot ROM over it, and FF50 lands on UNMAPPED or COMPAT, which the PPU checkpoint follows for FLG bit 3; without `--boot` the post-boot state is a labelled snapshot). Ordinary STOP, mode-3 length, the VRAM and OAM locks, the serial cable and a CGB's OAM DMA from E000-FFFF are on by default, in the reference and in weights (`docs/hardware-tests.md` §3): the PPU checkpoint emits each line's mode-3 length (`ML`), which reaches the control checkpoint through `ppu::Lengths` as a late input its pass asks for (`MQ`); control emits the GBC CPU's access locks and how long they hold (`LK`, `MX`, `MY`, `Lines::locks`), the memory checkpoint reads them as CTL bits 5-7 and asks for them (RQ bit 7, late slot `LK`) when they lapsed; an access OAM DMA blocks lands in `layout::BLOCKED`, where the host cuts the run. `io::Link` is a serial cable between two sessions (`Session::link`, `run_linked_frame`), the control checkpoint's `SI`, `SX` and `SO`. `GBCFORMER_ACCESS_TIMING=1` is the prototype of M-cycle access timing, reference GBC CPU only (`Core::access_cycles`, `docs/hardware-tests.md` §4.1).
- **Library surface.** `Session` (`session.rs`) runs a game frame by frame and returns `Event`s (a battery save to persist); it never touches the filesystem. `Session::ram_byte` reads work RAM and high RAM as the game left it (from the model's memory when it holds them), which the tests use. `frontend::play` runs a session in a window with the keyboard as the buttons; `Pacer` is the one frame clock and drops debt rather than bursting. `PressScript` (`press.rs`) is the `--press` format, and `Hardware::resolve` the header-to-console rule.
- **`lockstep.rs`.** `Lockstep` runs a candidate core beside the reference; it stops at the first divergence. Each checkpoint device compares at its own pass boundaries, so its lockstep is its own (`apu_circuit::ApuLockstep`, `control_circuit::ControlLockstep`, `ppu_circuit::PpuModel` under `--lockstep ppu`).
- **`stack.rs`.** Which components run in weights. `Stack` is a `Backend` (host, model, lockstep) per `Component` (cpu, memory, ppu, apu, control), plus whether they share one checkpoint (`--one-model`). `Stack::resolve` applies the dependency table (`Component::requires`), refuses `--one-model` without memory in weights, and names the checkpoints to compile (`Checkpoints`: the CPU side's `Weights`, the PPU's, APU's and control's own, or the one checkpoint). `Stack::build` compiles each engine once (`Engines::new`) and hands it to its builder: `AnyCore`, the enum of built cores a `Session` runs, and the APU, control and PPU devices `Session::with_stack` puts in the machine's slots. Memory lockstep is `Core::audit`, the model's fetches and reads held to the host's bytes every step.
- **`one_model.rs`.** The whole Game Boy as one Llama checkpoint (`--one-model`, `docs/one-model.md`). The six circuits (`one_model::Part`: ppu, cpu with memory, apu, control, the PPU's mode-3 length with the judge of each display write, `ppu_circuit::circuit::build_length`, and the pixel FIFO's stepper, `ppu_circuit::stepper`, which draws the lines the judge marks, `docs/ppu-in-weights.md` §14.2b) are concatenated into one circuit and compiled once; each part runs as a stream over the shared weights (`Engine::streams`), with its own sequence and engine state. The parts overlay their wires on the same residual channels, and each stream runs only its own prefix of channels, layers, units and heads (`Model::stream`, read from the GGUF by `gguf::load_slice`; `docs/hardware-shaped.md` §15). A stream's `View` (in `engine/view.rs`) maps its own slots and tokens onto the checkpoint's, holding every other part's slot at a fixed token, and `Plan::prune` cuts the checked fast plan to what the stream's tokens can reach. The CPU stream owns the memory's KV cache; the PPU, length and stepper streams follow its records (the length stream answers each line's mode-3 length as the line is handed over, and the PPU's own `ML` is asserted against it). A layer's MLP units and heads are the sum over the parts placed there, and a stock runtime's uniform file gives every layer the widest layer's, so `one_model::circuit` re-levels the PPU's three parts into the layers the GBC CPU, the APU and the control logic leave (`level.rs`: `Graph::pack` from the last layer down, a head moving with its query and its readers; `one_model::PLACEMENT`). The parts share the input slots (`Circuit::parts`: a part's k-th input without nibble wires holds slot k, the GBC CPU's inputs with nibble wires slots of their own), layer 0 gathers each group of slots once for every part that holds it (`Model::groups`, `Overlay::holders`), every holder's bit wire sits in the channel the gather writes (`Circuit::overlay_channels`), and every output mask keys on a fallback dim 128 below each gather's targets, so a stock runtime's pass decodes only the stream's own slots (`one_model::group`, `docs/stock-llama.md` §12a). The CLI refuses `--one-model` unless memory is in weights, and `tools/gate.sh` runs Yellow CGB 300 with every component in weights, in lockstep, as one model, then again with the step oracle on every stream (`docs/one-model.md` §4).

## Gates for any change to the circuit, emitter or engine

All three must hold:
1. The circuit and the checkpoint each pass all 500,000 SST cases.
2. The engine produces exactly the dense pass's tokens.
3. `run --frames 8 --core lockstep --hardware dmg` reaches frame hash `6872b003…`, and `run --frames 300 --core lockstep` (CGB) reaches `cfd31f3d…`, with no divergence.

`tools/gate.sh` runs them all, plus `tools/conflict-markers.sh`, `tools/dead-citations.sh` and `tools/speed-switch.sh` (skipped without `vendor/daid` or `magick`), and then each component's gate with it in weights and its reference in lockstep: `instr_timing` with `cpu,control`, `dmg_sound` 01-04 with `apu,control`, both acid2 images with `cpu,memory,ppu,control`, and Yellow, Crystal, Zelda DX and Mario DX for 300 frames with all five (`cfd31f3d`, `ccfe7ad3`, `f10b2b4a`, `ea7f86ca`; Zelda DX and Mario DX switch to double speed, `docs/perf-log.md` "CGB double speed").

For performance work, use the median of 3 runs and add a row to `docs/perf-log.md`.

The host checkpoint's digest (`cargo run --release --example digest`) is `bebf5d93…` (70.4M dense parameters). A refactor that keeps it left the checkpoint bit-identical. It last moved when the step's inputs became the fetched stream and the circuit's immediates OP1 and OP2 under the HALT bug too (`docs/hardware-tests.md` §3; `188ee397…` before). Before that it moved when the OAM corruption bug's idle M-cycle events (`MC` bits 3-6) joined every GBC CPU circuit (`docs/hardware-tests.md` §4.4; `76c89995…` before them, `fac7fab8…` before the pixel FIFO's work), when the GBC CPU circuits gained the dispatch's vector after the high byte's push, HALT staying on itself and the operand count (`docs/hardware-tests.md` §3.11), when they gained the access cycles `RC` and `WC` (§4.1), and when nibble channels became the GBC CPU's default (`docs/perf-log.md`, "d4 the default"). The 0/1 GBC CPU variant was removed; its digests are in `docs/perf-log.md`. The memory circuit's changes (the hardware-shaped GBC CPU, `docs/hardware-shaped.md` §2.6) leave it unchanged and move cpu-memory and the one model (a change to the memory heads' key layout moves the PPU too), and `docs/perf-log.md` records them; a change that moves it on purpose records the new digest and the reason there and here.

## Each component in weights, and its gate

The CPU, memory, PPU, APU and control logic each run in weights, and each keeps the CPU's rules: exact by construction, held in lockstep to its reference device with the first divergence stopping the run, every engine shortcut guarded, and no device silently supplying a result. The reference devices sit behind the `Device` contract (`device.rs`).

- **Contract.** No change moves these hashes: `run --frames 8 --core lockstep --hardware dmg` `6872b003…`, `run --frames 300 --core lockstep` (CGB) `cfd31f3d…`, `tools/bench/text.sh` `870aa3fd…`, `tools/bench/overworld.sh` `822059c1…`, `tools/bench/battle.sh` `d3534543…`, dmg-acid2 and cgb-acid2 pixel-exact (`tools/acid2.sh`), blargg `cpu_instrs`, `instr_timing` and `dmg_sound` 01 to 04. The CPU checkpoint stays token-identical (`cargo test --release --test checkpoint_sst`), and a speed claim is text.sh and overworld.sh interleaved A/B against the previous binary, median of 3, with a row in `docs/perf-log.md`.
- **Memory.** Attention-cache memory: the cartridge prefilled as cells of the cache, a write replacing its line's cell, and a read one attention head whose query matches the address (`docs/memory-in-weights.md`). It was chosen over a DeltaNet-style recurrent memory layer, which lies outside the Llama layer set, after both matched a reference byte array over random read/write streams and over the CPU memory traffic of a Yellow run (`docs/perf-log.md`, "Memory prototypes"); that prototype and its benchmark were removed afterwards. The dense pass is the oracle, and an engine shortcut (an address index) runs only behind a guard proving it equals the attention result.
- **PPU.** The PPU checkpoint runs in lockstep with the `ppu.rs` line renderer per scanline: requests, next state and the 160 pixels compared, first divergence stops. dmg-acid2 and cgb-acid2 are pixel-exact with the checkpoint rendering, and `run --frames 300 --core lockstep` on Pokémon Yellow, Pokémon Crystal, Link's Awakening DX and Super Mario Bros. Deluxe reaches the same frame hash with the checkpoint rendering as with the reference renderer. It is its own checkpoint on its own thread (`docs/ppu-in-weights.md` §9); the palette lookup, the window line counter and the display registers (LCDC, SCX, SCY, WX and WY, as records the bus writes, `docs/ppu-in-weights.md` §12) are in the model.
- **APU.** The APU checkpoint runs in lockstep with `apu.rs` per segment: next state and the sample stream compared, first divergence stops. blargg `dmg_sound` 01 to 04 pass with the checkpoint generating the sound.
- **Control logic.** The CPU lockstep hashes above, blargg `instr_timing`, and `tests/interrupt_fuzz.rs` with timer-driven IRQs, all with the compiled control logic.
- **Every checkpoint.** Dense parameters and nonzeros reported (`cargo run --release --example shape`), and the host runs the reference device behind the checkpoint only in lockstep or when labelled, as `--warmup` labels reference frames.
